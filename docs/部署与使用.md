# 部署与使用

面向把 yeyu 装到内网 Linux 服务器、并把免签名桌面客户端发给组员的完整操作说明。
所有命令都在仓库根 `yeyu/` 下执行，除非另行注明 `cd`。

> 版本信息：Node.js 24 / pnpm 11 / Fastify 4 / Prisma 5（SQLite）/ Electron 33 + electron-builder 25。
> 本文件描述的行为均与代码一致：服务端 `server/src/index.ts`、`server/src/app.ts`、`server/src/lib/storage.ts`、桌面端 `desktop/electron/main.ts`。

---

## 1. 系统组成、端口与数据文件

| 组成 | 说明 |
| --- | --- |
| 服务端 | Fastify，监听 `PORT`（默认 **4000**），监听地址 `HOST`（默认 `0.0.0.0`，即局域网可访问） |
| 健康检查 | `GET /api/health` → `{ "ok": true, "at": "<ISO 时间>" }`，无需鉴权 |
| 数据库 | **SQLite 单文件**：`server/prisma/dev.db`（`DATABASE_URL="file:./dev.db"`，相对路径以 `server/prisma/` 为基准） |
| 上传文件 | `UPLOAD_DIR`（默认 `./uploads`，相对服务端工作目录 → `server/uploads/`），按 `YYYY-MM/` 分桶 |
| 桌面客户端 | Electron；首次运行在「用户数据目录」写 `config.json`，内容 `{ "serverUrl": "http://127.0.0.1:4000" }`，登录页可改 |

服务端环境变量（`server/.env` 或容器环境）：

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `DATABASE_URL` | 是 | `file:./dev.db` | SQLite 文件地址；相对路径以 `server/prisma/` 为基准，容器里用绝对路径 `file:/data/app.db` |
| `JWT_SECRET` | **生产必改** | 代码内置开发密钥 | 签发 7 天 JWT；换掉它等于让所有已登录客户端失效 |
| `PORT` | 否 | `4000` | 服务端口 |
| `HOST` | 否 | `0.0.0.0` | 监听地址；只想本机访问可设 `127.0.0.1` |
| `UPLOAD_DIR` | 否 | `./uploads` | 附件/图片落盘目录，**必须与数据库一起备份** |
| `LOG_LEVEL` | 否 | `info` | Fastify 日志级别 |

**备份 = 数据库文件 + uploads 目录，两者必须一起备份、一起恢复**（数据库里只存文件的相对路径）。

## 2. 服务器准备

### 2.1 依赖与账号

```bash
# 以 Ubuntu 22.04/24.04、Debian 12 为例
sudo apt update && sudo apt install -y git curl unzip sqlite3
# Node.js 20+（实测 Node 24）
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt install -y nodejs
# pnpm 11
sudo npm i -g pnpm@11
node -v && pnpm -v
```

内网无法直连 GitHub 时，先把 npm 源与 Electron 镜像切到国内（仓库已内置，见第 5 节）：

```bash
npm config set registry https://registry.npmmirror.com
```

### 2.2 裸机部署（推荐给「一台内网服务器 + 少量组员」的场景）

```bash
sudo mkdir -p /opt/yeyu && sudo chown "$USER" /opt/yeyu
git clone <内网仓库地址> /opt/yeyu
cd /opt/yeyu

# 1) 安装依赖（含 server 的 prisma/tsx，桌面端依赖在部署机可不装，见下方说明）
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
pnpm install

# 2) 准备环境变量
cp server/.env.example server/.env
# 必改：JWT_SECRET 换成随机长串
head -c 48 /dev/urandom | base64 | tr -d '\n'      # 生成一个随机密钥
vim server/.env

# 3) 建表
pnpm db:push

# 4) 创建首个管理员（幂等，可重复执行）
pnpm db:seed

# 5) 启动（前台，便于先验证）
cd server && pnpm start
# 另开一个终端验证
curl -s http://127.0.0.1:4000/api/health
```

**只部署服务端时可以不装桌面端依赖**：`pnpm install --filter @yeyu/server...`（会连带装上 `shared`），
但仓库的 `pnpm-lock.yaml` 是整仓锁定的，某些 pnpm 版本对「只装部分包」会报 lockfile 不一致，
最省事的做法仍然是完整 `pnpm install`（约 600MB，含 Electron 二进制），部署完可再 `rm -rf desktop/node_modules`。

**让服务常驻**（二选一）：

```bash
# A. systemd
sudo tee /etc/systemd/system/yeyu.service >/dev/null <<'EOF'
[Unit]
Description=yeyu server
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/yeyu/server
EnvironmentFile=/opt/yeyu/server/.env
ExecStart=/usr/local/bin/pnpm start
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now yeyu
sudo journalctl -u yeyu -f     # 看日志
```

```bash
# B. pm2
sudo npm i -g pm2
cd /opt/yeyu/server && pm2 start "pnpm start" --name yeyu
pm2 save && pm2 startup
```

### 2.3 Docker Compose 部署

> ⚠️ 本机（打包这台 Mac）**没有 Docker**，`deploy/docker-compose.yml` 只做了 YAML 语法校验与文件级检查，
> 未在真实 Docker 上跑过 `compose up`。首次上线请预留时间观察 `docker compose logs -f server`。

```bash
cd /opt/yeyu/deploy

# 1) 环境变量：JWT_SECRET 必填，缺失时 compose 会直接报错退出
cp .env.example .env
vim .env      # 至少改 JWT_SECRET

# 2) 构建镜像并启动（第一次要装依赖，5~10 分钟）
docker compose up -d --build

# 3) 看状态与健康
docker compose ps
docker compose logs -f server
curl -s http://127.0.0.1:4000/api/health

# 4) 创建首个管理员（容器内已带 tsx/prisma，工作目录 /app/server）
docker compose exec server pnpm exec tsx prisma/seed.ts
```

镜像要点（`deploy/Dockerfile`）：

- 基础镜像 `node:24-bookworm-slim`，内装 `pnpm@11.21.0`、`openssl`（Prisma SQLite 引擎依赖）、`tini`。
- 运行时用 `tsx` 直接跑 TypeScript，因此镜像保留 devDependencies（`prisma`、`tsx` 都在 devDependencies）。
- 数据全部在命名卷 **`yeyu-data`** 的 `/data` 下：`/data/app.db` + `/data/uploads/`。
  一个卷 = 一次备份，容器重建不丢数据。
- 容器启动时默认执行 `prisma db push --skip-generate` 同步表结构；想自己控制时机就设 `SKIP_DB_PUSH=1`。
- 健康检查用容器内 Node 的 `fetch` 打 `/api/health`，`docker compose ps` 会显示 `healthy`。

常用命令：

```bash
cd /opt/yeyu/deploy
docker compose restart server        # 重启
docker compose logs -f --tail=200 server
docker compose down                  # 停容器（卷保留）
docker compose down -v               # 停容器并删卷（= 删库，慎用）
```

### 2.4 反向代理 / HTTPS（可选）

内网有域名或要上 HTTPS 时用 `deploy/nginx.conf.example`：

```bash
sudo cp deploy/nginx.conf.example /etc/nginx/conf.d/yeyu.conf
sudo vim /etc/nginx/conf.d/yeyu.conf    # 改 server_name、证书路径
sudo nginx -t && sudo systemctl reload nginx
```

注意：附件上传上限是 20MB（`MAX_UPLOAD_BYTES`），示例里已设 `client_max_body_size 25m`。
客户端填服务器地址时，直接填 nginx 的对外地址（如 `http://yeyu.example.internal`）。

## 3. 首次启动与首个管理员

1. 服务起来后确认健康检查：
   ```bash
   curl -s http://127.0.0.1:4000/api/health
   # {"ok":true,"at":"2026-11-10T13:55:00.000Z"}
   ```
2. 执行 seed（裸机 `pnpm db:seed`；容器 `docker compose exec server pnpm exec tsx prisma/seed.ts`）。
   脚本幂等：管理员已存在就跳过，不会覆盖密码。
3. 用首个管理员登录客户端：

   | 项 | 值 |
   | --- | --- |
   | 手机号 | `SEED_ADMIN_PHONE` 环境变量；未设置时为 **`13800000000`**（仅演示） |
   | 密码 | `SEED_ADMIN_PASSWORD` 环境变量；未设置时为 **`Admin@123456`**（仅演示） |

4. **登录后第一件事：改掉初始密码**（用户管理 → 重置密码），或直接改环境变量后重建库。
5. 其他组员自行在登录页「注册」，注册出来的账号是 `PENDING`（待审批）状态，登录会被拒绝，
   需要管理员在「用户与权限」里审批为 `ACTIVE`。管理员也可以直接新建账号并指定角色。

seed 的可选参数：

```bash
# 额外写入 5 条示例资产（DEMO-0001 ~ DEMO-0005，按 code 幂等）
SEED_DEMO=1 pnpm db:seed

# 指定首个管理员密码
SEED_ADMIN_PASSWORD='Xx@2026#lab' pnpm db:seed
```

> 生产别开 `SEED_DEMO=1`，示例资产会出现在正式台账里（每条备注都写了「示例数据，可安全删除」）。

## 4. 客户端指向内网地址

Windows/macOS 客户端默认连 `http://127.0.0.1:4000`，连不上就要改地址：

1. 打开客户端 → 登录页 → 「服务器地址」填 `http://<服务器内网 IP>:4000`（例：`http://10.20.30.15:4000`），保存后再登录。
2. 地址会写进配置文件的 `serverUrl` 字段，下次启动自动使用：
   - macOS：`~/Library/Application Support/Yeyu/config.json`
   - Windows：`%APPDATA%\Yeyu\config.json`（即 `C:\Users\<用户名>\AppData\Roaming\Yeyu\config.json`）
3. 也可以直接编辑该文件后重启客户端：
   ```json
   { "serverUrl": "http://10.20.30.15:4000" }
   ```
4. 连通性自查（在客户端机器上执行）：
   ```powershell
   # Windows
   Test-NetConnection 10.20.30.15 -Port 4000
   ```
   ```bash
   # macOS / Linux
   curl -s http://10.20.30.15:4000/api/health
   ```

## 5. 构建安装包（Windows / macOS，免签名）

配置在 `desktop/electron-builder.yml`：`appId=com.yeyu.desktop`、`productName=页屿`、
`identity: null`（不签名、不公证）、产物输出到 `desktop/release/`。

```bash
cd <项目目录>   # 例：~/yeyu

# macOS（当前架构；也可以 scripts/build-mac.sh arm64 / x64 指定）
scripts/build-mac.sh
# 只出可执行目录、不压 dmg 的最快验证（约 40 秒）
cd desktop && npx --no-install electron-builder --dir --mac

# Windows NSIS 安装包（x64）—— 在 macOS/Linux 上交叉构建也可以，实测通过
scripts/build-win.sh
```

产物（`desktop/release/`）：

| 产物 | 路径 | 实测（本机 arm64 macOS，2026-11-10） |
| --- | --- | --- |
| macOS 可执行目录 | `desktop/release/mac-arm64/Yeyu.app` | ✅ 233MB（`electron-builder --dir --mac`） |
| macOS dmg | `desktop/release/yeyu-0.1.0-mac-arm64.dmg` | ✅ 94MB（未签名、未公证，APFS 打包） |
| Windows 安装包 | `desktop/release/yeyu-0.1.0-win-x64-setup.exe` | ✅ 78MB（在 macOS 上交叉构建成功，免签名；正式发布仍建议在 Windows 上构建） |

### 5.1 免签名的两个后果

- **macOS**：首次打开提示「无法验证开发者」或「已损坏」。解决办法（任选其一）：
  ```bash
  /usr/bin/xattr -cr /Applications/Yeyu.app     # 去掉隔离属性
  ```
  或在 Finder 里 **右键 App → 打开 → 再点「打开」**。
- **Windows**：首次运行触发 SmartScreen「Windows 已保护你的电脑」。点「更多信息」→「仍要运行」。
  组内分发建议直接说明这一步，避免被当成病毒。

### 5.2 内网/离线安装依赖的三个坑（本机都踩过）

1. **Electron 二进制下载**：GitHub 不通时必须走镜像。
   ```bash
   export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
   pnpm install
   ```
   仓库 `.npmrc` 已配置 `electron_mirror` 与 `electron_builder_binaries_mirror`，正常 `pnpm install` 即可。
2. **pnpm 11 的 strictDepBuilds**：默认会把「未批准的依赖构建脚本」判为错误，
   仓库已用 `.npmrc`（`strict-dep-builds=false`）与 `pnpm-workspace.yaml`（`strictDepBuilds: false` +
   `ignoredBuiltDependencies`）关掉。如果你的环境不读这两处（例如换了包管理器版本），还有两条路：
   ```bash
   pnpm approve-builds                 # 交互式勾选 electron / esbuild / prisma 等，写入 approval
   # 或
   pnpm config set strict-dep-builds false
   ```
   > 注意：本仓库**禁止**新增依赖；该命令只在安装 electron 等「已声明依赖」的构建脚本时使用。
3. **Prisma 引擎**：`@prisma/client` 的 postinstall 被忽略（`ignoredBuiltDependencies`），
   所以首次部署/容器构建都必须显式执行一次 `pnpm --filter @yeyu/server exec prisma generate`
   （`pnpm db:push`、seed、测试都会间接用到；Dockerfile 已内置这一步）。

## 6. 备份与恢复

**备份 = 数据库文件 + uploads 目录。** 数据库里只存附件的相对路径，单独备份 db 会让所有图片变成死链。

### 6.1 裸机部署

```bash
cd /opt/yeyu

# 备份（默认 server/prisma/dev.db + server/uploads → backups/yeyu-backup-<时间戳>.tar.gz）
scripts/backup.sh

# 指定输出目录、只保留最近 7 个
scripts/backup.sh /mnt/nas/lab-backups
KEEP=7 scripts/backup.sh /mnt/nas/lab-backups

# 每天 02:30 自动备份（crontab -e）
30 2 * * * cd /opt/yeyu && KEEP=14 scripts/backup.sh /mnt/nas/lab-backups >>/var/log/lab-backup.log 2>&1
```

脚本行为：优先用 `sqlite3 ".backup"` 做一致性快照（没装 sqlite3 时退化为 `cp`），
再把 `uploads/` 一并打包，归档内附 `MANIFEST.txt`（时间、来源、文件数、恢复命令）。

恢复（**先停服务**，SQLite 运行中被覆盖会损坏）：

```bash
sudo systemctl stop yeyu                # 或 pm2 stop yeyu
cd /opt/yeyu
scripts/restore.sh backups/yeyu-backup-20261110-030000.tar.gz          # 预演，只打印将要覆盖什么
scripts/restore.sh backups/yeyu-backup-20261110-030000.tar.gz --yes    # 真正恢复
sudo systemctl start yeyu
curl -s http://127.0.0.1:4000/api/health
```

恢复脚本会先把现状另存为 `backups/pre-restore-<时间戳>.tar.gz`，覆盖前还会留 `dev.db.bak-<时间戳>`，
所以误操作还有回退余地。

### 6.2 Docker Compose 部署

数据库和 uploads 都在卷 `yeyu-data` 的 `/data` 下，最稳的做法是「停服务 → 从容器里把 /data 拷出来 → 打包」：

```bash
cd /opt/yeyu

# 1) 停服务，保证没有写入
(cd deploy && docker compose stop server)

# 2) 把容器内 /data 拷到宿主机（容器处于 stopped 状态也能 docker cp）
rm -rf backups/volume-snapshot && mkdir -p backups
docker cp yeyu:/data backups/volume-snapshot

# 3) 用同一个脚本打包（复用已测过的 backup.sh）
DB_FILE="$PWD/backups/volume-snapshot/app.db" UPLOAD_DIR="$PWD/backups/volume-snapshot/uploads" scripts/backup.sh

# 4) 起服务
(cd deploy && docker compose start server)
```

恢复（同样先停服务）：

```bash
cd /opt/yeyu
(cd deploy && docker compose stop server)

# 1) 解包到暂存目录（用 restore.sh，目标指向暂存目录）
rm -rf /tmp/restore && mkdir -p /tmp/restore
BACKUP_DIR=/tmp/restore-bak DB_FILE=/tmp/restore/app.db UPLOAD_DIR=/tmp/restore/uploads \
  scripts/restore.sh backups/yeyu-backup-20261110-030000.tar.gz --yes

# 2) 覆盖容器内 /data（先清空 uploads，避免旧文件残留）
docker cp /tmp/restore/app.db yeyu:/data/app.db
(cd deploy && docker compose run --rm --entrypoint sh server -c 'rm -rf /data/uploads && mkdir -p /data/uploads')
docker cp /tmp/restore/uploads/. yeyu:/data/uploads

# 3) 起服务并验证
(cd deploy && docker compose start server && docker compose logs --tail=50 server)
```

> 上述 docker 恢复步骤依赖 `docker cp` 与 `docker compose run --rm`，未在本机验证（无 Docker）。

## 7. 升级

**先备份，再升级。** 升级只涉及代码与表结构，数据文件（db + uploads）原地保留。

裸机：

```bash
sudo systemctl stop yeyu
cd /opt/yeyu
scripts/backup.sh                                    # 1. 备份
git pull                                             # 2. 取新代码
pnpm install                                         # 3. 依赖有变化时
pnpm db:push                                         # 4. 同步表结构（只加列/加表，不删数据；会提示可能丢数据的变更，务必看清）
sudo systemctl start yeyu                   # 5. 起服务
curl -s http://127.0.0.1:4000/api/health
```

Docker：

```bash
cd /opt/yeyu
scripts/backup.sh                                    # 按 6.2 先做快照
git pull
cd deploy && docker compose up -d --build            # 容器启动时自动 prisma db push
docker compose logs -f server
```

升级注意事项：

- `prisma db push` **不会**自动执行 seed；首个管理员只在首次部署时创建一次。
- 客户端升级：把新的安装包替换旧的即可，配置（`config.json`）保留，不需要重新填服务器地址。
- 服务端与客户端版本不强制同步，但接口契约变更会要求两端一起升级（见 `docs/API.md` 的变更记录）。

## 8. 常见故障

### 8.1 客户端连不上服务器（Windows 防火墙最常见）

症状：客户端登录页报「网络错误 / Network Error / Failed to fetch」，但服务器本机 `curl` 正常。

排查顺序：

1. 服务器本机 `curl -s http://127.0.0.1:4000/api/health` 通不通？不通 → 服务没起来或端口不是 4000。
2. 从客户端机器测端口：`Test-NetConnection <服务器IP> -Port 4000`（PowerShell）或 `curl -s http://<服务器IP>:4000/api/health`。
3. **服务器是 Windows**：放行入站 4000（管理员 PowerShell）：
   ```powershell
   New-NetFirewallRule -DisplayName "yeyu 4000" -Direction Inbound -Protocol TCP -LocalPort 4000 -Action Allow
   ```
   或在「Windows Defender 防火墙 → 高级设置 → 入站规则 → 新建规则 → 端口 → TCP 4000 → 允许」。
4. **服务器是 Linux**：`sudo ufw allow 4000/tcp`（或 firewalld `sudo firewall-cmd --add-port=4000/tcp --permanent && sudo firewall-cmd --reload`）。
5. 云主机还要检查安全组是否放行 4000。
6. 客户端地址填的是和服务器同一网段的内网 IP，不要填 `127.0.0.1` 或 Docker 网桥地址。

### 8.2 端口被占用

症状：启动报 `EADDRINUSE: address already in use 0.0.0.0:4000`。

```bash
# macOS / Linux
lsof -nP -iTCP:4000 -sTCP:LISTEN
kill -9 <PID>

# Windows
netstat -ano | findstr :4000
taskkill /PID <PID> /F
```

换端口的正确做法：改服务端 `PORT`（`server/.env` 或容器 `APP_PORT`），
并同步改客户端登录页里的服务器地址（端口不一致是最常见的「改完还是连不上」）。
注意 `desktop` 的 Vite 开发服务器固定占 5173（`strictPort`），本机开发时别占用。

### 8.3 SQLite 打不开 / 读写失败

症状（服务端日志）：`PrismaClientInitializationError`、`unable to open database file`、
`SqliteError: attempt to write a readonly database`、`EACCES`。

原因与处理：

| 原因 | 处理 |
| --- | --- |
| 目录属主不对 | `sudo chown -R <运行用户>:<运行用户> /opt/yeyu/server/prisma /opt/yeyu/server/uploads` |
| 目录只读（挂载/权限） | `ls -ld server/prisma` 确认有 `w`，容器部署检查卷是否 `:ro` |
| SELinux | `sudo chcon -Rt svirt_sandbox_file_t <数据目录>`（或 `setsebool -P container_manage_cgroup on`） |
| 放在网络盘/NFS 上 | **不要**把 SQLite 放在 NFS/SMB 上，锁语义不可靠；必须放本地磁盘或 Docker 命名卷 |
| 多实例共用一个 db 文件 | 只允许一个服务端进程/容器；SQLite 单文件不支持多写者，会报 `database is locked` |
| 磁盘满 | `df -h`；SQLite 写失败几乎都伴随 `disk I/O error` |

### 8.4 上传/图片 404 或预览空白

- 检查 `UPLOAD_DIR` 与备份是否一致：换机器后只拷了 db 没拷 `uploads/`，图片全部 404。
- 图片在客户端通过带 token 的查询参数访问（`?token=<jwt>`），token 过期（7 天）后需重新登录。
- 反向代理记得放行 20MB 以上的请求体（`client_max_body_size 25m`），否则大附件报 413。

### 8.5 客户端白屏 / 打不开

- macOS 上被 Gatekeeper 拦：`/usr/bin/xattr -cr /Applications/Yeyu.app` 后重开。
- Windows SmartScreen：更多信息 → 仍要运行。
- 白屏但端口连通：多半是服务器地址带了路径或多余斜杠，填 `http://IP:4000` 即可（客户端会去掉结尾的 `/`）。

### 8.6 `pnpm install` 失败

- `ERR_PNPM_...` 关于构建脚本：见 5.2 的 `pnpm approve-builds`。
- Electron 下载超时：设置 `ELECTRON_MIRROR`（见 5.2）。
- Prisma 报「Client is not generated」：`pnpm --filter @yeyu/server exec prisma generate`。
